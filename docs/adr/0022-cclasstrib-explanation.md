# ADR 0022 — Why does a cClassTrib have its treatment? A cited explanation from the provisions of the bridge

**Status:** accepted (`pipelines/rtc/rtc04_explain.py`, DAG `dag_rtc_explain` on the asset `datalabs://gold/rtc`
emitted by `dag_rtc_ref.publish_rtc`, table `ai.rtc_cclasstrib_explicacao` in
`infra/postgres/init/sql/10_rtc_explain.sql`, golden cases `pipelines/rtc/explain_golden.yml`, checks `rtc_explain_*`,
NF-e board row "Explicação por cClassTrib"). The plumbing is measured on the real table with a scripted model; the
model's own level is measured by the first lab run, which writes `pipelines/rtc/explain_baseline.yml`.

**Context.** The bridge (ADR 0021) tells an auditor *where* in the LC 214 each official cClassTrib is grounded:
`200038 → art. 138`. It does not say *why* the classification has its treatment ("alíquota reduzida em 60%",
"diferimento com redução", "imunidade") in words a reader can check. The LC 214 RAG generates cited answers
(ADR 0015), but it stalls on retrieval: the auditor's vocabulary misses the law's (2 of 9 dev phrasings answered).
For this question that problem is gone: the provisions are known before any search, deterministically, from the
Receita's own reference. Decisions taken with the owner (2026-11-22): the input is a cClassTrib (not an NF-e item);
the output is text generated by the LLM from the provisions, with the law cited as the source.

**Decisions.**

1. **The bridge is the anchor; no vector search.** For each row of `silver.rtc_cclasstrib` the context is the
   articles of the provisions the bridge linked (`resolved`, `resolved_by_text`), each rendered by the retriever's
   own `build_block` with no hits: the whole article when it fits `LC214_ANCHOR_MAX_TOKENS` (2,000), else its caput,
   the cited subtree and the labels left out. Measured on table 1.7.2 × law `0cf36f4433ce`: 202 classifications,
   176 distinct anchor sets, context p50 439 tokens, p90 1,109, max 1,938, against a budget of 3,696: nothing is cut.
2. **The table's facts go in the prompt, after the law.** Description, tax group, CST, treatment, type of rate,
   reduction per tax (only when above 0: a 0 in the table means "no reduction", not "rate zero"), annex (in roman
   numerals, as the law names it), the Receita's published reference and the validity. Deterministic text (no
   "today"): it is part of the row's fingerprint. Law first, facts last, so classifications grounded in the same
   provisions share the prompt's whole prefix; the plan runs them back to back. Whether Ollama reuses that prefix
   is a hypothesis the lab run measures (`prompt_eval_count` per row and in `ai.llm_call`).
3. **The generator's barriers, not new ones.** The same JSON Schema, options (`temperature 0`, seed, `num_ctx`
   6144) and decision rule (`model_text`) as lc06: the model's `answerable`, then every citation from the field and
   from the text, resolved by the router's parser and checked against the provisions the context showed. No valid
   citation left → `refused`, with the model's own text kept in `resposta_modelo`. A classification with no linked
   provision ("Regra Geral", another law only) gets a fixed text and no LLM call (`no_anchor`). The shown
   explanation carries `fontes` ("art. 138, § 2º"): the law cited as the source.
4. **Two deterministic checks per row.** `cita_ponte`: a valid citation falls on a provision of the bridge or inside
   it. Strict on purpose: the caput of art. 138 for an anchored § 2º points the reader at the wrong text, so it does
   not count (the generator's `same_branch` would accept it). `numeros_sem_fonte`: percentages the explanation
   states that neither the facts nor the law shown carry. An invented rate is the costliest error for this reader.
   The facts include the Receita's own reference, which makes `cita_ponte` easy by design: it measures whether the
   model follows its anchor, not whether it can find one.
5. **Incremental and resumable, row by row.** Each row stores a fingerprint of everything that decides its text:
   the prompt (context and facts), the prompt version, the model and its digest, `EXPLAIN_VERSION`. A run generates
   only the rows whose fingerprint changed (a new table version that leaves a classification untouched keeps its
   text; the lineage columns are restamped). Each row commits on its own. A new classification gets a placeholder
   row (`pendente`, no outcome); an old one waiting for regeneration keeps its text, flagged `pendente`. A run spends
   at most `RTC_EXPLAIN_MAX_MINUTES` (80) and the next one continues: the same convergence as the vector sync
   (ADR 0007), without its full rebuild (the old explanations stay readable). A budget that generated nothing exits
   99, not 0.
6. **A DAG of its own, on an asset.** ~1 min per classification on CPU, ~3 h for a new model or prompt (estimated
   from lc06's measured rates, ~25 tokens/s of prompt and ~12/s of answer, for ~900 prompt tokens): inside
   `dag_rtc_ref` it would hold the 45-min deadline and the RTC health checks hostage. `dag_rtc_ref` emits
   `datalabs://gold/rtc` once the reference, the bridge and the RTC models are built (`publish_rtc`, daily);
   `dag_rtc_explain` decides per row whether there is work, so most runs exit 99 in seconds. Not ready → 99 with the
   cause named: law not served (`law_not_loaded`), bridge not built from the reference and law in use
   (`bridge_not_current`), silver not built from the reference in use (`silver_not_current`), no Ollama
   (`llm_unavailable`). Ollama lost in the middle of a run is a failure (exit 1), and the next run resumes.
7. **Ten golden cases, generated first, plus a human verdict.** `explain_golden.yml` covers the kinds of treatment
   and the hard spots of the bridge: a 60% reduction on a whole article, one code with two treatments (CBS zero,
   IBS 60%), a range (art. 127, I a XVIII), a list (§ 1º, I e II), the "matriz/filial" vocabulary (art. 6º, II), the
   reference resolved by the transcription (art. 80), a transcription that diverges from the law (art. 485), a
   paragraph of the same article as another case (art. 138, § 2º), the Imposto Seletivo, and "Regra Geral"
   (`no_anchor`). Per case: outcome, an expected provision cited, the table's rates stated. Ids are re-checked
   against the law served on every run (`explain_golden_stale`). The owner reads them with `--review` and records
   `verdict` + the `sha` he read; a verdict whose sha is not the current text's is reported `stale`.
8. **Gate against a committed baseline, written after a measured run.** Rates (`explained_pct`, `cites_bridge_pct`,
   the three golden rates) may drop at most `RTC_EXPLAIN_TOLERANCE_CASES` (1) of their own n; rows with numbers
   without source may not grow at all (like false answers in ADR 0015). The golden part is judged once every golden
   case is current, the batch part once nothing is pending. No baseline → the gate warns and passes: the model
   cannot be measured from CI or from a cloud session, so the first full lab run measures and `--write-baseline`
   records it (refused while rows are pending).
9. **Usage per call** through `llm_usage` (ADR 0018), `app = rtc_explain`, tags `cclasstrib`, `grupo`, `outcome`.

**Measured (2026-11-22, table 1.7.2 × law `0cf36f4433ce`, local Postgres 16, scripted model).** The scripted model
writes the Receita's reference and the table's rates in its text and leaves the citation field empty (the path of
qwen2.5:3b under `model_text`). It tests the code around the model, not the model:

| Run | Result |
|---|---|
| first | 202 rows in ~1 s: 200 `explained`, 2 `no_anchor`; golden 10/10 (outcome, expected provision, rates) |
| again, same inputs | exit 99, 0 calls |
| model digest changed | 200 regenerated, the 2 `no_anchor` kept (no model in them) |
| budget 0 | exit 99, 200 rows `pendente` with their previous text; the next run drains them |
| baseline written, then a model that invents a rate in every third answer | gate fails: `numbers_ungrounded` 66 > 0 |
| checks `rtc_explain_*`, the 5 board queries | pass / run |

`cita_ponte` came out at 98% with the scripted text: the 4 misses are alíneas written in prose as "Art. 200, II, a da
LC" (the router reads a bare "a" as an alínea only at the end of a reference, since "a" is also a Portuguese word),
so the citation lands on the inciso, outside the anchor. That is the model's prose, not the bridge, and the real
model will write its own; the check reports it either way.

**Consequences.**
- The first full run is ~3 h of CPU in the lab (drained in 80-min runs, or one manual run with a larger
  `--max-minutes`); then `python -m pipelines.rtc.rtc04_explain --write-baseline`, review the file, commit it.
- 2 checks (`rtc_explain_pending`, `rtc_explain_numbers_without_source`, warn, `requires: ai`): 34 in total.
- An explanation is shown only with a citation of what the model read; a refusal says which barrier stopped it.
  This is the first AI output in the lab whose context is decided by data, not by retrieval: a weak result here
  is the model's, since the context is right by construction.
- Next: the NF-e item → explanation join in dbt (via `cltr_id`, like `vw_nfe_item_fundamento_lc214`); a larger or
  hosted model behind the same `LLM` interface, measured against this baseline.
